# Secrets

Encrypted in git, mounted as files at runtime, and enforced by the build.

```
secrets/
  registry.yaml       which secrets exist, who gets them, where they're required
  common.enc.env      values shared by every environment
  local.enc.env       overlay for `tilt up` / `make run`
  prod.enc.env        overlay for `make run env=prod`
  .sops.yaml          age recipients
  manage.py           the CLI — all of it
```

## Everyday use

```sh
./secrets/manage.py ls                    # what exists, where it's set (never values)
./secrets/manage.py set MAPBOX_TOKEN      # prompts, no echo, no shell history
./secrets/manage.py get prod MAPBOX_TOKEN # explicit read
./secrets/manage.py add NEW_KEY --description "…" --consumers backend
./secrets/manage.py rm OLD_KEY
```

Then commit. The production release archive carries the encrypted vault to the
deploy host, which decrypts it with its own age key.

`make run`, `make run env=prod`, `tilt up` and `make data-fetch` all work
unchanged; they wrap themselves in `manage.py exec`.

## Why it is shaped this way

The list of secret *names* used to live in four hand-maintained places —
`application*.yaml`, `.env.example`, `docker-compose.yml`, and a deploy
workflow — kept in sync by a script somebody had to remember to run. It drifted:
`CAMPFLARE_TOKEN` was read by the backend and documented nowhere, and
`env_file: .env` handed every secret to a container that needed none.

So there is now exactly one list, and **everything else is generated from it or
checked against it**:

| artifact | how it stays true |
| --- | --- |
| `docker-compose.secrets.yml` | generated by `manage.py generate`; CI runs `--check` |
| per-service least privilege | falls out of `consumers` — a wrong entry means the container genuinely doesn't get the secret |
| `application*.yaml` agreement | `SecretRegistryDriftTest` fails the build both ways |
| required-at-boot | `SecretsBootstrap` refuses to start, listing every missing secret |
| host scripts | `test_secrets.py` greps `scripts/` for unregistered credentials |

Adding a secret is one registry edit. Forgetting any downstream step fails CI
with the exact diff, rather than surfacing in production.

## How values reach processes

Nothing is ever decrypted to disk.

1. `manage.py exec <env> --` merges `common` + the environment overlay in
   memory and `execvpe`s the command with the values in its environment.
2. Docker Compose reads them to resolve `docker-compose.secrets.yml`, which
   declares each secret as `environment:`-sourced.
3. Compose mounts each one at `/run/secrets/<name>` inside only the containers
   that declare it.

So containers read **files**, and the values appear in neither `docker inspect`
nor the host process table.

| consumer | mechanism |
| --- | --- |
| postgres | `POSTGRES_PASSWORD_FILE` (the image's own `file_env`) |
| grafana | `GF_SECURITY_ADMIN_PASSWORD__FILE`; provisioning uses `$__file{}` |
| backend | `SecretsBootstrap` copies `/run/secrets/*` into system properties before Ktor parses config, so they never become environment variables |
| cloudflared | `TUNNEL_TOKEN_FILE` — not `--token`, which would put it on the command line |
| host scripts | environment injection from `exec`; there is nowhere to mount a file outside a container |

**What this does and doesn't protect.** It removes the durable plaintext
artifact — the file that gets committed by accident, swept into a backup, or
left on a decommissioned host — and it stops secrets reaching containers that
have no use for them. It does not make a running process's memory private, and
anyone with root on the host or `docker exec` can read a mounted secret.

## First-time setup on a new host

Needs `sops` and `age` (`brew install sops age`, or `make install`).

```sh
./secrets/manage.py init
```

Writes an age identity to `~/.config/sops/age/keys.txt` — the same path on
every platform, so runbooks stay copy-pasteable — and prints its public half.
Add that to `secrets/.sops.yaml`, then from a host that can already decrypt:

```sh
./secrets/manage.py rotate
```

**The private key is not in the repo and cannot be recovered.** Back it up.

## Rotation

Two different things, routinely confused:

- **`manage.py rotate`** re-wraps the vaults' data key for the current
  recipient list. Use it when adding or removing a holder. It does *not* revoke
  anyone: git history keeps every past ciphertext, and a removed holder's key
  still opens it.
- **Rotating a credential** means issuing a new value at Mapbox, Clerk, Slack…
  and `manage.py set`-ing it. This is the only thing that actually revokes
  access, and it's the right response whenever a key is lost, a holder is
  removed, or a value is exposed.

## Not in the vault, on purpose

- **`TESLA_COOKIES`** — Akamai binds `_abck` to the egress IP that minted it, so
  one shared copy would give every host a cookie only one can use. Mint it
  manually per machine: tesla.com/findus → click a Supercharger → DevTools
  Network → `get-charger-details` → copy the `Cookie` header value into
  `TESLA_COOKIES=` in `.env.local` (gitignored, per-machine).
- **GitHub Actions secrets** (`TS_OAUTH_*`, `DEPLOY_SSH_KEY`, `CODECOV_TOKEN`) —
  credentials *for* the pipeline, not runtime config. Keeping them in GitHub is
  what lets CI hold no decryption key at all.

## Known gap: the three passwords already baked into volumes

`POSTGRES_PASSWORD`, `GRAFANA_DB_PASSWORD` and `GRAFANA_ADMIN_PASSWORD` are in
the vault at their current values (`roadtrip`, `roadtrip`, `admin`), because
that is genuinely what the running stack uses.

Changing them in the vault is not enough. Postgres only applies
`POSTGRES_PASSWORD` when initialising an empty data directory, and Grafana only
applies the admin password when creating the admin user. Both are already
persisted, so a new value would leave the client using it and the server still
expecting the old one. A real rotation is:

```sql
ALTER USER roadtrip WITH PASSWORD '…';
ALTER ROLE grafana_reader WITH PASSWORD '…';
```

plus `grafana-cli admin reset-admin-password` — then `manage.py set` to match.

## Troubleshooting

**`sops failed … did not find keys in locations`** — sops lists only the
environment variables it checked, so a key in the wrong directory looks exactly
like no key. `manage.py init` adopts a stranded key and tells you it did.

**`missing required secret(s) for profile 'prod'`** — the boot validator did its
job. It lists all of them at once; `manage.py ls` shows where each is set.

**`docker-compose.secrets.yml is stale`** — the registry changed without
regenerating. `./secrets/manage.py generate`.

## ENCRYPTION_KEY rotation

`ENCRYPTION_KEY` seals per-user secrets in `user_settings` (`*_cipher`
columns). Rotating it orphans every existing blob: decryption fails
per-user and degrades gracefully (no Slack alert / no stored rec.gov
password) rather than throwing, and affected users must re-enter their
stored secrets. Rotate deliberately, not routinely.
